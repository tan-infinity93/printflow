  PRINTING APP — DATABASE-BACKED SAAS BACKEND RECOMMENDATIONS
  Date   : 06 June 2026
  Purpose: Scope review document for transitioning the browser-only printing
           app to a multi-tenant, cloud-persisted SaaS product.

This document is structured as a decision framework. Each section presents
options with trade-off notes so you can pick what fits your timeline, budget,
and target user base before dev scope is finalised.


────────────────────────────────────────────────────────────────────────────────
1. WHAT CHANGES WHEN YOU ADD A BACKEND
────────────────────────────────────────────────────────────────────────────────

Current state (browser-only)          SaaS backend adds
-------------------------------        --------------------------------
IndexedDB per browser / device         Centralised DB — works on any device
No sharing or collaboration            Shared documents, team workspaces
No real auth (plain password hash)     JWT / OAuth, secure session tokens
No billing / access tiers              Subscription management, usage metering
Data lost if browser storage cleared   Durable server-side persistence
Manual "Export RAW File" for backup    Auto-save, cloud drafts, history
Single user per browser tab            Multi-user, role-based access control

2. RECOMMENDED DATABASE ARCHITECTURE
────────────────────────────────────────────────────────────────────────────────

2.1  PRIMARY DATABASE — PostgreSQL (recommended)
─────────────────────────────────────────────────
Why: Relational structure suits this app well — users own documents,
     documents have versions, templates belong to workspaces, audit logs
     are append-only rows. PostgreSQL's JSONB column type lets you store
     the existing dom-json canvas snapshots without a schema migration
     every time the canvas format evolves.

Hosted options (no infra management):
  • Supabase (PostgreSQL + realtime + built-in auth + storage) — best
    all-in-one for a solo/small team. Free tier available.
  • Neon (serverless PostgreSQL, scales to zero) — good for low-traffic
    starts, pay-per-query.
  • PlanetScale (MySQL-compatible, branching) — good if team is familiar
    with MySQL. No JSONB but JSON column available.
  • Railway / Render managed PostgreSQL — simple self-contained option.

Alternative: MongoDB Atlas
  • Pros: schema-less suits the flexible canvas JSON structure.
  • Cons: loses relational integrity for users ↔ documents ↔ billing;
    harder to do complex queries for analytics/metering later.
  Recommend only if team has strong MongoDB familiarity.

2.2  CACHING LAYER — Redis (optional, add later)
─────────────────────────────────────────────────
Use for:
  • Session tokens / JWT blacklisting
  • Rate limiting (per user / per IP)
  • Caching frequently read templates (gallery)
  • Pub/sub for real-time collaboration events

Hosted: Upstash Redis (serverless, free tier) or Redis Cloud.

2.3  FILE / ASSET STORAGE — Object Storage
────────────────────────────────────────────
Current app stores images as base64 inside IndexedDB / canvas JSON.
At scale this is expensive (large row sizes, slow reads).

Recommendation: move image assets to object storage.
  • Cloudflare R2 — no egress fees, S3-compatible API. Best cost option.
  • AWS S3 — most ecosystem support.
  • Supabase Storage — built-in if using Supabase, simplest integration.

Images are uploaded once and referenced by URL in the canvas JSON.
Canvas snapshots become slim JSON blobs rather than base64-bloated payloads.

2.4  SEARCH (FUTURE)
──────────────────────
Template and document search can start with PostgreSQL full-text search
(ts_vector on document name / tags). Upgrade to Typesense or Algolia
if the template gallery grows large (1 000+ templates).

  user_id       uuid FK → users
  token_hash    text
  expires_at    timestamptz

  org_id        uuid FK → organisations

  document_id   uuid FK → documents

  org_id        uuid FK → organisations (NULL = global/built-in)

  name          text
  page_type     text

  canvas_json   jsonb
  thumbnail_url text
  is_public     boolean DEFAULT false
  created_at    timestamptz

template_assets                       (images referenced by templates)
  id            uuid PK
  template_id   uuid FK → templates
  storage_key   text  (object storage path)
  mime_type     text

  id            uuid PK
  org_id        uuid FK → organisations
  stripe_sub_id text
  plan          text
  status        text  (active | trialing | past_due | cancelled)
  current_period_end timestamptz

usage_events                          (for metering / analytics)
  id            uuid PK
  org_id        uuid FK → organisations
  user_id       uuid FK → users
  event_type    text  (pdf_export | document_save | template_load | ...)
  created_at    timestamptz

4. API LAYER RECOMMENDATIONS
────────────────────────────────────────────────────────────────────────────────

4.1  FRAMEWORK
───────────────
Option A — Node.js + Fastify  (recommended)
  • Fast, low-overhead, JSON-first
  • TypeScript support
  • Can reuse the existing JS canvas serialisation logic server-side
  • Easy to deploy on Railway, Render, Fly.io

Option B — Next.js API Routes / App Router (full-stack)
  • Good if you want to serve the frontend and API from one deployment
  • Built-in Vercel deployment
  • Slightly heavier for pure API work

Option C — Supabase Edge Functions (if using Supabase)
  • Zero infrastructure, but limited compute per request
  • Best for lightweight triggers (audit log, webhook handling)
  • Not ideal for PDF generation (heavy compute)

4.2  AUTHENTICATION
────────────────────
  • Use JSON Web Tokens (JWT) for stateless auth
  • Short-lived access tokens (15 min) + refresh tokens (7 days) in
    httpOnly cookies — prevents XSS token theft
  • OAuth providers to support: Google, GitHub (most requested by devs)
  • Managed auth options: Supabase Auth, Clerk, Auth.js (NextAuth)
    All handle token rotation, OAuth flows, and email verification.

4.3  KEY API ENDPOINTS
───────────────────────
POST   /auth/register
POST   /auth/login
POST   /auth/refresh
DELETE /auth/logout

GET    /documents                  (list — paginated, filterable)
POST   /documents                  (create)
GET    /documents/:id              (fetch with canvas_json)
PATCH  /documents/:id              (update name, page_size, canvas_json)
DELETE /documents/:id              (soft delete → is_archived)
POST   /documents/:id/export-pdf   (server-side PDF render — see §6)

GET    /documents/:id/versions     (version history)
POST   /documents/:id/versions     (save current as named version)
POST   /documents/:id/versions/:vid/restore

GET    /templates                  (gallery — org + public)
POST   /templates                  (create custom template)
DELETE /templates/:id

POST   /assets/upload              (presigned URL or direct upload)

GET    /audit-logs                 (paginated, filterable by user/action)

GET    /billing/plans
POST   /billing/checkout           (Stripe checkout session)
POST   /billing/portal             (Stripe customer portal)
POST   /billing/webhook            (Stripe webhook handler)

GET    /org/usage                  (current period usage stats)

4.4  REALTIME (OPTIONAL — PHASE 2)
────────────────────────────────────
For collaborative editing (two users on the same document):
  • Supabase Realtime (Postgres change streams via websocket)
  • Or Liveblocks / PartyKit (purpose-built multiplayer primitives)
  Start with "last write wins" on document save. Operational transform
  or CRDT (Yjs) collaboration can be a Phase 2 feature.

5. MULTI-TENANCY MODEL
────────────────────────────────────────────────────────────────────────────────

Recommended: shared database, row-level isolation
  • All tenants in one PostgreSQL instance
  • Every table has an org_id foreign key
  • All queries include WHERE org_id = ? filter enforced at the API layer
  • Row-Level Security (RLS) in PostgreSQL as a second safety layer
    (critical if using Supabase which exposes the DB directly)

This approach is the simplest to start with and can handle thousands of
organisations before needing schema-per-tenant isolation.

User roles within an organisation:
  owner   — full access, billing management
  admin   — manage users, templates, all documents
  editor  — create and edit own documents, use all templates
  viewer  — read-only, can download/export but not edit


────────────────────────────────────────────────────────────────────────────────
6. SERVER-SIDE PDF GENERATION
────────────────────────────────────────────────────────────────────────────────

Current approach: html2canvas + jsPDF in-browser (rasterised, not vector).

For SaaS, move PDF generation server-side:

Option A — Puppeteer / Playwright (recommended for fidelity)
  • Spin up a headless Chromium, load the canvas HTML, capture PDF
  • True vector PDF with proper fonts
  • Run as a separate microservice (high memory — 300–500 MB per render)
  • Hosting: Fly.io machines (scale to zero), AWS Lambda container,
    Modal.com (pay-per-render)

Option B — PDFKit / pdf-lib (Node.js native, no browser)
  • Pure JS, very fast, no Chromium dependency
  • Must translate canvas dom-json into PDFKit draw calls server-side
  • More development effort but smaller infrastructure footprint

Option C — Keep browser-side for MVP
  • Zero backend cost for PDF generation
  • Perfectly viable for v1 SaaS; upgrade to server-side in v2 when
    quality or reliability becomes a customer complaint

Recommendation: keep browser-side PDF for MVP (Phase 1), add Playwright
microservice in Phase 2 when PDF quality is a selling point.

8. FRONTEND MIGRATION PATH
────────────────────────────────────────────────────────────────────────────────

The existing plain HTML / JS app can be migrated incrementally:

Phase 1 — Backend auth + storage only
  • Keep the frontend exactly as-is
  • Replace IndexedDB calls (saveRecordToDB, getAllRecordsFromDB) with
    fetch() calls to the new API
  • User logs in → gets JWT → all DB calls go to server
  • Documents auto-save every captureSnapshot() call (debounced 3s)
  • IndexedDB kept as offline cache / fallback draft

Phase 2 — React / Next.js rewrite (optional)
  • Move to a component-based frontend for maintainability
  • The SVG canvas logic (layout.js, canvas-elements.js,
    canvas-interactions.js) can be wrapped in React refs — the SVG
    manipulation is all DOM-based so it ports cleanly
  • Route structure: /login  /dashboard  /editor/:documentId
    /templates  /settings  /billing

Phase 3 — Collaboration + mobile
  • Real-time cursor sharing
  • Touch-optimised UI (already started in canvas-interactions.js)
  • Progressive Web App (PWA) for offline editing

10. RECOMMENDED DEVELOPMENT PHASES
────────────────────────────────────────────────────────────────────────────────

PHASE 1 — BACKEND CORE  (4–6 weeks)
  ✦ PostgreSQL schema (users, organisations, documents, templates,
    audit_logs) — see §3
  ✦ Node.js / Fastify API with JWT auth
  ✦ Replace IndexedDB in frontend with API calls:
      - document CRUD (save, load, list)
      - template CRUD
      - audit log writes
  ✦ Supabase Auth or custom auth with bcrypt + JWT
  ✦ Basic org management (invite user, set role)
  Deliverable: working app with cloud persistence, no billing

PHASE 2 — BILLING + TIERS  (2–3 weeks)
  ✦ Stripe integration (checkout, webhook, portal)
  ✦ Plan enforcement middleware (document count limits, page limits)
  ✦ Usage metering (log PDF exports, template loads)
  ✦ Email notifications (welcome, invoice, plan change)
  Deliverable: monetisable product with Free + Pro tiers

PHASE 3 — TEAM FEATURES  (3–4 weeks)
  ✦ Organisation invites + multi-seat management
  ✦ Shared template gallery (org-scoped)
  ✦ Document sharing with view/edit link
  ✦ Version history with named saves + restore
  ✦ Audit log UI + export
  Deliverable: Team tier fully functional

PHASE 4 — QUALITY + SCALE  (ongoing)
  ✦ Server-side PDF generation (Playwright microservice)
  ✦ Full-text document / template search
  ✦ Real-time collaboration (Supabase Realtime or Liveblocks)
  ✦ API access for programmatic document creation
  ✦ SSO / SAML for Enterprise tier
  ✦ PWA / mobile support

11. ITEMS TO DECIDE BEFORE SCOPING DEV
────────────────────────────────────────────────────────────────────────────────

Decision 1 — Frontend rewrite or incremental migration?
  Rewrite to React now → higher upfront cost, cleaner long-term
  Incremental → ship faster, accumulate some tech debt

Decision 2 — Auth provider or custom?
  Managed (Supabase Auth / Clerk) → fast, handles edge cases (MFA, OAuth)
  Custom → full control, no vendor dependency, more to build/maintain

Decision 3 — All-in-one (Supabase) or best-of-breed?
  Supabase: database + auth + storage + realtime in one dashboard
            fastest to start, some lock-in
  Best-of-breed: Neon + Clerk + R2 + Upstash
            more flexible, slightly more DevOps work

Decision 4 — Pricing model validation
  Run a waitlist / landing page before building billing
  Confirm price sensitivity with target users before Phase 2

Decision 5 — Multi-region?
  Start single-region (us-east or eu-west depending on user base)
  Add read replicas or edge caching in Phase 4

12. EXISTING CODE ASSETS THAT CARRY OVER UNCHANGED
────────────────────────────────────────────────────────────────────────────────

These files require zero modification to work with a backend:
  canvas-elements.js    — SVG element creation
  canvas-interactions.js— drag, context menu, z-order
  layout.js             — canvas multi-page structure
  darkmode.js           — theme toggle
  style.css             — all styles

These files need API call wrappers replacing IndexedDB helpers:
  scripts.js            — replace saveRecordToDB / getAllRecordsFromDB /
                          getSingleRecordFromDB / deleteSingleRecordFromDB
                          with fetch() wrappers pointing to the new API
  letters.js            — no change (uses canvas functions only)
  exports.js            — minor change: POST to /documents/:id/export-pdf
  imports.js            — minor change: GET /documents/:id for import
  stats.js              — replace getAllRecordsFromDB with API calls
  help.js               — no change

The swap is clean because all IndexedDB access already flows through
four helper functions in scripts.js. Replacing those four functions
with fetch-based equivalents switches the entire app to the backend
without touching any other file.
